# Exception Handling

Exception handling is a mechanism for handling abnormal conditions during program execution so that an application can respond gracefully instead of terminating unexpectedly.

It helps maintain controlled program flow, improve reliability, and provide meaningful error information.

## 1. Exception vs Error

Both exceptions and errors are subclasses of `Throwable`.

| Exception | Error |
|---|---|
| Represents conditions an application may handle | Represents serious JVM or system-level problems |
| Often recoverable | Generally not recoverable |
| Can be handled using try-catch | Usually should not be caught |
| Example: `IOException`, `ArithmeticException` | Example: `OutOfMemoryError`, `StackOverflowError` |

**Important:** An application can technically catch an `Error`, but catching serious JVM errors is generally not a reliable recovery strategy.

## 2. Exception Hierarchy

Java's exception hierarchy starts with `Throwable`.

```text
Object
  └── Throwable
       ├── Error
       │    ├── OutOfMemoryError
       │    └── StackOverflowError
       │
       └── Exception
            ├── IOException
            ├── SQLException
            │
            └── RuntimeException
                 ├── NullPointerException
                 ├── ArithmeticException
                 ├── ArrayIndexOutOfBoundsException
                 └── IllegalArgumentException
```

Two important categories:

- **Checked exceptions:** Checked by the compiler.
- **Unchecked exceptions:** Not checked by the compiler.

## 3. Checked vs Unchecked Exceptions

### Checked Exceptions

These are exceptions other than `RuntimeException` subclasses (and their subclasses), within the `Exception` branch.

The compiler requires them to be either:
- Handled using `try-catch`, or
- Declared using `throws`.

Examples:
- `IOException`
- `SQLException`
- `ClassNotFoundException`
- `InterruptedException`

```java
public void readFile() throws IOException {
    FileReader reader = new FileReader("data.txt");
}
```

### Unchecked Exceptions

These include:
- `RuntimeException` and its subclasses.
- `Error` and its subclasses.

The compiler does not require explicit handling or declaration.

Common RuntimeException examples:

| Exception | Typical cause |
|---|---|
| `NullPointerException` | Accessing a member through null |
| `ArithmeticException` | Integer division by zero |
| `ArrayIndexOutOfBoundsException` | Invalid array index |
| `NumberFormatException` | Invalid string-to-number conversion |
| `IllegalArgumentException` | Invalid argument passed to a method |
| `ClassCastException` | Invalid runtime type cast |
| `IllegalStateException` | Method called in an inappropriate state |

Example:

```java
int result = 10 / 0; // ArithmeticException
```

### Comparison

| Checked | Unchecked |
|---|---|
| Compiler enforces handling/declaration | Compiler does not enforce handling/declaration |
| Subclasses of Exception excluding RuntimeException | RuntimeException subclasses and Error subclasses |
| Often represent external or recoverable conditions | Often indicate programming errors or invalid state |
| Example: IOException | Example: NullPointerException |

**Interview point:** Checked exceptions are a compile-time checking requirement. It does not mean the exception necessarily occurs at compile time.

## 4. Default Exception Handling

If an exception is not handled, it propagates up the call stack.

If no suitable handler is found, the JVM's default exception handler:
- Prints the exception type and message.
- Prints the stack trace.
- Terminates the affected thread.

For an uncaught exception in the main thread, the application typically terminates if no other non-daemon threads keep it running.

Example:

```java
public class Main {
    public static void main(String[] args) {
        int result = 10 / 0;
        System.out.println(result);
    }
}
```

The second statement is not executed because the exception interrupts normal execution.

## 5. Stack Trace

A stack trace shows the sequence of method calls active when an exception occurred.

Example:

```text
Exception in thread "main" java.lang.ArithmeticException: / by zero
    at Calculator.divide(Calculator.java:10)
    at Service.calculate(Service.java:20)
    at Main.main(Main.java:5)
```

How to read it:
- The exception type identifies the problem.
- The message gives additional context.
- The first stack frame generally identifies where the exception was thrown.
- Subsequent frames show the calling methods.

Useful methods:

```java
try {
    int result = 10 / 0;
} catch (ArithmeticException e) {
    System.out.println(e.getMessage());
    e.printStackTrace();
}
```

| Method | Purpose |
|---|---|
| `getMessage()` | Returns the exception message |
| `printStackTrace()` | Prints the stack trace |
| `toString()` | Returns exception class name and message |
| `getCause()` | Returns the underlying cause, if present |

## 6. try-catch-finally

### try block

Contains code that may throw an exception.

### catch block

Handles a matching exception.

### finally block

Contains cleanup code that normally executes whether an exception occurs or not.

```java
try {
    int result = 10 / 0;
    System.out.println(result);
} catch (ArithmeticException e) {
    System.out.println("Cannot divide by zero");
} finally {
    System.out.println("Cleanup executed");
}
```

Output:

```text
Cannot divide by zero
Cleanup executed
```

### Multiple catch blocks

A try block can have multiple catch blocks.

```java
try {
    int[] numbers = {10, 20};
    System.out.println(numbers[5]);
} catch (ArithmeticException e) {
    System.out.println("Arithmetic error");
} catch (ArrayIndexOutOfBoundsException e) {
    System.out.println("Invalid array index");
} catch (Exception e) {
    System.out.println("General exception");
}
```

### Catch block ordering

Always place more specific exception types before their parent types.

```java
try {
    // Risky code
} catch (FileNotFoundException e) {
    // Specific handling
} catch (IOException e) {
    // General I/O handling
} catch (Exception e) {
    // Broad fallback handling
}
```

This is invalid:

```java
try {
    // Risky code
} catch (Exception e) {
    // General handling
} catch (IOException e) {
    // Compilation error: unreachable catch block
}
```

The parent catch already handles the subclass.

### Multi-catch

Java allows multiple unrelated exception types in one catch block using `|`.

```java
try {
    // Risky code
} catch (IOException | SQLException e) {
    System.out.println(e.getMessage());
}
```

The alternatives in a multi-catch must not have a subclass-superclass relationship.

## 7. Nested try-catch

A try-catch block can exist inside another try-catch block.

```java
try {
    System.out.println("Outer try");

    try {
        int result = 10 / 0;
    } catch (ArithmeticException e) {
        System.out.println("Inner catch");
    }

} catch (Exception e) {
    System.out.println("Outer catch");
}
```

The inner catch handles the exception because it matches the exception type.

If the inner block does not handle an exception, it propagates to the outer block.

Nested exception handling is valid, but avoid unnecessary nesting because it makes control flow harder to understand.

## 8. finally Block: Important Rules

The `finally` block normally executes:
- When no exception occurs.
- When an exception is caught.
- When an exception is not caught.
- When a `return` statement executes in the try or catch block.

However, it is not guaranteed to execute in every possible situation. For example:
- JVM termination using `System.exit()`.
- JVM crash or abrupt process termination.
- Other conditions preventing normal execution.

### Return in finally

Avoid returning from a `finally` block.

```java
static int calculate() {
    try {
        return 10;
    } finally {
        return 20;
    }
}
```

This returns `20`, overriding the pending return from the try block.

Returning from `finally` can also suppress an exception. It is a bad practice.

## 9. throw vs throws

These two keywords have different purposes.

### throw

Used to explicitly throw an exception.

```java
if (age < 18) {
    throw new IllegalArgumentException("Age must be at least 18");
}
```

### throws

Used in a method declaration to specify exceptions that may propagate to the caller.

```java
public void readFile() throws IOException {
    FileReader reader = new FileReader("data.txt");
}
```

| throw | throws |
|---|---|
| Used inside method or block | Used in method or constructor declaration |
| Actually throws an exception | Declares possible exceptions |
| Followed by an exception object | Followed by exception class names |
| Throws one exception object at a time | Can declare multiple exception types |

Example with both:

```java
public void validate(int age) throws IOException {
    if (age < 18) {
        throw new IllegalArgumentException("Underage");
    }
}
```

## 10. Custom Exceptions

Custom exceptions allow applications to represent domain-specific failure conditions.

### Custom checked exception

Extend `Exception`.

```java
public class InvalidAgeException extends Exception {
    public InvalidAgeException(String message) {
        super(message);
    }
}
```

Usage:

```java
public void validateAge(int age) throws InvalidAgeException {
    if (age < 18) {
        throw new InvalidAgeException("Age must be 18 or above");
    }
}
```

The caller must handle or declare the checked exception.

### Custom unchecked exception

Extend `RuntimeException`.

```java
public class InsufficientBalanceException extends RuntimeException {
    public InsufficientBalanceException(String message) {
        super(message);
    }
}
```

Usage:

```java
public void withdraw(double balance, double amount) {
    if (amount > balance) {
        throw new InsufficientBalanceException("Insufficient balance");
    }
}
```

### When to use which?

| Checked custom exception | Unchecked custom exception |
|---|---|
| Extends `Exception` | Extends `RuntimeException` |
| Caller must handle or declare | Caller is not forced by compiler |
| Suitable when callers are expected to handle a recoverable condition | Often suitable for invalid arguments, business-rule violations, or programming errors, depending on API design |

Choose based on the contract of the API and whether callers are reasonably expected to recover.

## 11. Try-with-Resources

Java 7 introduced try-with-resources to automatically close resources.

It is useful for:
- File readers and writers.
- Database connections.
- Prepared statements and result sets.
- Input/output streams.
- Other resources implementing `AutoCloseable`.

Traditional approach:

```java
FileReader reader = null;

try {
    reader = new FileReader("data.txt");
    // Read file
} catch (IOException e) {
    e.printStackTrace();
} finally {
    if (reader != null) {
        try {
            reader.close();
        } catch (IOException e) {
            e.printStackTrace();
        }
    }
}
```

Try-with-resources:

```java
try (FileReader reader = new FileReader("data.txt")) {
    // Read file
} catch (IOException e) {
    e.printStackTrace();
}
```

The resource is automatically closed when execution leaves the try block, whether normally or exceptionally.

### AutoCloseable vs Closeable

- `AutoCloseable` is the general interface for resources that can be closed.
- `Closeable` extends `AutoCloseable` and is commonly used for I/O resources.
- `AutoCloseable.close()` can declare `Exception`.
- `Closeable.close()` declares `IOException`.

### Multiple Resources

```java
try (
    FileReader reader = new FileReader("input.txt");
    BufferedReader bufferedReader = new BufferedReader(reader)
) {
    System.out.println(bufferedReader.readLine());
}
```

Resources are closed automatically in reverse order of declaration.

### Suppressed Exceptions

If the try block throws an exception and closing a resource also throws an exception, the try-block exception remains the primary exception. The close exception is recorded as a suppressed exception.

Retrieve suppressed exceptions using:

```java
for (Throwable suppressed : e.getSuppressed()) {
    System.out.println(suppressed);
}
```

## 12. Exception Propagation

When a method throws an exception and does not handle it, the exception propagates to its caller.

```java
static void methodA() {
    int result = 10 / 0;
}

static void methodB() {
    methodA();
}

public static void main(String[] args) {
    try {
        methodB();
    } catch (ArithmeticException e) {
        System.out.println("Handled in main");
    }
}
```

The exception travels from `methodA()` to `methodB()` and then to `main()`, where it is handled.

For checked exceptions, each method in the call chain must handle the exception or declare it appropriately.

## 13. Best Practices

- Catch specific exceptions instead of unnecessarily catching `Exception`.
- Do not silently swallow exceptions.
- Preserve the original exception when wrapping or rethrowing.
- Include meaningful context in exception messages.
- Use try-with-resources for resource management.
- Do not use exceptions for normal program flow.
- Avoid overly broad catch blocks.
- Do not log an exception and rethrow it repeatedly at every layer; this can create duplicate logs.
- Do not catch `Error` for routine application recovery.
- Create custom exceptions when they add meaningful domain context.
- Avoid returning from `finally`.

### Exception Wrapping

When translating a low-level exception into an application-specific exception, preserve the cause.

```java
try {
    // Database operation
} catch (SQLException e) {
    throw new DataAccessException("Unable to fetch employee", e);
}
```

The original exception is available through `getCause()`.

## 14. Interview Questions

**1. What is the difference between Exception and Error?**

Exceptions represent conditions applications may handle. Errors represent serious JVM or system-level problems that generally should not be handled as routine application failures.

**2. What is the difference between checked and unchecked exceptions?**

Checked exceptions must be caught or declared. RuntimeException subclasses and Error subclasses are unchecked.

**3. Can we have a try block without a catch block?**

Yes, if it has a `finally` block or is a try-with-resources statement.

**4. Can we have multiple catch blocks?**

Yes. They must be ordered from more specific exceptions to more general exceptions.

**5. Does finally always execute?**

No. Abrupt JVM or process termination can prevent it from executing.

**6. Can we throw an exception from finally?**

Yes, but an exception thrown from `finally` can replace an exception already propagating from `try` or `catch`. Avoid this unless intentional.

**7. Can we override a method and declare a broader checked exception?**

No. An overriding method cannot declare broader checked exceptions than the overridden method allows. It may declare narrower checked exceptions or no checked exceptions. Unchecked exceptions are not subject to this restriction.

**8. What happens if a catch block throws another exception?**

The new exception propagates to the caller unless another suitable handler catches it. The original exception may be lost unless it is preserved as the cause.

**9. Difference between final, finally, and finalize()?**

| Term | Meaning |
|---|---|
| `final` | Keyword used for constants, preventing method overriding, or preventing inheritance |
| `finally` | Exception-handling block used for cleanup |
| `finalize()` | Legacy garbage-collection-related method; deprecated and should not be used for resource management |

**10. What is try-with-resources?**

A Java feature that automatically closes resources implementing `AutoCloseable` when the try block exits.

**11. What is a suppressed exception?**

An exception thrown while closing a resource when another exception is already propagating. It is attached to the primary exception and can be retrieved using `getSuppressed()`.
