# Encapsulation & Access Modifiers

## Encapsulation
- Bundles data (fields) and behavior (methods) into a class.
- **Data hiding:** Restricts direct access to internal state and exposes controlled operations.
- Common approach: `private` fields with public getters/setters where appropriate.
- Setters can enforce validation and maintain object invariants; getters/setters are not mandatory for every field.

```java
class BankAccount {
    private double balance;

    public double getBalance() {
        return balance;
    }

    public void deposit(double amount) {
        if (amount <= 0) {
            throw new IllegalArgumentException("Amount must be positive");
        }
        balance += amount;
    }
}
```

Prefer meaningful operations such as `deposit()` over unrestricted setters when they better protect an object's valid state.

## Access Modifiers

| Modifier | Accessibility |
|---|---|
| `private` | Same class only |
| No modifier (package-private) | Same package |
| `protected` | Same package + subclasses, subject to cross-package access rules |
| `public` | Wherever the declaring type/member is accessible |

- Top-level classes can generally be `public` or package-private, not `private` or `protected`.
- A subclass in another package accesses a `protected` instance member through inheritance rules; it cannot freely access that member through an arbitrary superclass instance.
- Access modifiers control visibility, not encryption.

## Encapsulation vs. Abstraction
- **Encapsulation:** Controls access to state and implementation through a defined boundary.
- **Abstraction:** Exposes essential operations while hiding unnecessary implementation details.
