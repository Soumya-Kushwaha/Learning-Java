# Immutable Classes

## Immutability
An object is **immutable** if its observable state cannot change after construction.

Benefits:
- Safer sharing between threads.
- Fewer unintended side effects.
- Easier reasoning, testing, and use as value objects.

## Design Rules
1. **Prevent subclassing** where necessary, commonly by declaring the class `final`.
2. Make fields `private` and `final`.
3. Initialize all required state through the constructor.
4. Do not expose setters or other state-mutating operations.
5. Defensively copy mutable inputs during construction.
6. Do not expose internal mutable state through getters; return defensive copies or immutable views/representations.
7. Ensure methods do not indirectly mutate the object's state.

## Example

```java
import java.util.ArrayList;
import java.util.List;

public final class Team {
    private final String name;
    private final List<String> members;

    public Team(String name, List<String> members) {
        this.name = name;
        this.members = new ArrayList<>(members);
    }

    public String getName() {
        return name;
    }

    public List<String> getMembers() {
        return new ArrayList<>(members);
    }
}
```

- The constructor copies the supplied list, so later changes to the caller's list do not affect the `Team`.
- The getter returns a copy, so callers cannot mutate the internal list.
- `String` is immutable; the example assumes the list contains immutable `String` elements.

## Shallow vs. Deep Defensive Copying
- **Shallow copy:** Creates a new collection/object but retains references to nested elements.
- **Deep copy:** Also copies nested mutable elements to the required depth.
- If a class contains mutable objects, copying only the outer container may not be enough.
- If an operation needs to change a value, compute and return a **new** instance of the class rather than modifying the current one.

For example, `new ArrayList<>(members)` is sufficient for a list of immutable strings, but not necessarily for a list of mutable objects.

## Important Gotchas
- `final` prevents reassignment of a field; it does not make the referenced object immutable.
- `private` restricts access but does not itself guarantee immutability.
- No setters is not sufficient if mutable internal references are exposed.
- A `final` class is a common safeguard, not a universal requirement for every possible immutable design.
- Immutability can simplify concurrency, but it does not automatically make every operation involving the object thread-safe.
- Immutable collections such as `List.copyOf(input)` can be useful, but they are shallow copies and reject null elements.

## Common Immutable Java Types
Examples include `String`, `Integer`, `BigDecimal`, and `LocalDate`.

## Interview Takeaway
A robust immutable class controls all state at construction, prevents later mutation, and never exposes mutable internal state. Defensive copying is essential whenever mutable objects cross the class boundary.
