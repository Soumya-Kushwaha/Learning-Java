# JVM Memory Management & Garbage Collection

## 1. Why Memory Management?

Java manages memory automatically through the JVM and Garbage Collector (GC), unlike languages such as C++ where developers may manage memory manually.

The JVM allocates memory for objects and manages their lifecycle. Garbage Collection reclaims heap memory occupied by objects that are no longer reachable.

**Important:** Automatic memory management does not eliminate memory problems. Poor object lifecycle management can still cause memory leaks and `OutOfMemoryError`.

## 2. JVM Runtime Data Areas

The JVM divides memory into runtime data areas. Some are shared across threads, while others are created separately for each thread.

| Memory Area | Scope | Purpose |
|---|---|---|
| Heap | Shared | Stores objects and arrays |
| Method Area | Shared | Stores class-level structures and metadata |
| Java Stack | Per-thread | Stores method frames, local variables and intermediate computations |
| PC Register | Per-thread | Tracks the current JVM instruction |
| Native Method Stack | Per-thread | Supports execution of native methods |

### 2.1 Stack Memory

- Each thread has its own JVM stack.
- Stores stack frames created for method invocations.
- A frame contains:
  - Local variables and parameters
  - Operand stack
  - Reference to the runtime constant pool for the current class
  - Method execution bookkeeping
- Frames are pushed when methods are invoked and popped when methods complete.
- Uses a **Last-In, First-Out (LIFO)** structure.

Example:

```java
public class StackExample {
    public static void main(String[] args) {
        int number = 10;
        calculate(number);
    }

    static void calculate(int value) {
        int result = value * 2;
    }
}
```

Each method invocation gets its own stack frame. When `calculate()` finishes, its frame is removed.

**Important distinction:**
- Local primitive variables are stored in the frame.
- Local object variables hold references; the objects themselves are generally allocated on the heap.
- The exact physical placement of objects is a JVM implementation detail because optimizations such as escape analysis may eliminate or transform allocations.

**Stack error:**

`StackOverflowError` occurs when a thread's stack grows beyond its permitted size, commonly due to uncontrolled recursion.

```java
static void recursiveMethod() {
    recursiveMethod();
}
```

### 2.2 Heap Memory

- Shared among all JVM threads.
- Stores objects and arrays.
- Created when the JVM starts.
- Managed by the Garbage Collector.
- Instance fields are part of their containing objects.

Example:

```java
class Employee {
    int id;
}

public class HeapExample {
    public static void main(String[] args) {
        Employee employee = new Employee();
        employee.id = 101;
    }
}
```

Here:
- `employee` is a local reference in the method's stack frame.
- The `Employee` object is allocated on the heap in the usual execution model.

**OutOfMemoryError:** Occurs when the JVM cannot allocate an object because sufficient memory cannot be made available. It can also occur in JVM memory areas other than the heap.

### 2.3 Method Area

A logical, shared runtime area that stores class-level information, such as:

- Class and interface metadata
- Runtime constant pools
- Method and constructor information
- Field information
- Method bytecode

Static fields are associated with their declaring class, but their exact storage representation is JVM-implementation-dependent. Avoid assuming that every static variable is physically stored in the Method Area.

**HotSpot JVM:** The Method Area is commonly implemented using **Metaspace**, which uses native memory.

Before Java 8, HotSpot used **PermGen (Permanent Generation)** for much of this class metadata. PermGen was removed in Java 8 and replaced by Metaspace.

### 2.4 Program Counter (PC) Register

- Each JVM thread has its own PC register.
- Tracks the address of the JVM instruction currently being executed.
- Helps the JVM resume execution after thread switching.
- Its value is undefined while executing a native method.

### 2.5 Native Method Stack

Supports execution of native methods, typically written in languages such as C or C++ through JNI (Java Native Interface).

## 3. Heap Memory Structure

A traditional generational heap divides memory into:

<escape>
Heap
├── Young Generation
│   ├── Eden Space
│   ├── Survivor Space 0 (S0)
│   └── Survivor Space 1 (S1)
│
└── Old Generation (Tenured)
</escape>

This is a common design, not a requirement for every garbage collector.

### 3.1 Young Generation

New objects are commonly allocated in the Young Generation.

It contains:

- **Eden Space:** Initial allocation area for most new objects.
- **Survivor Spaces (S0 and S1):** Hold objects that survive young-generation collection.

Typical object lifecycle:

1. A new object is allocated in Eden.
2. A young-generation collection occurs.
3. Unreachable objects are reclaimed.
4. Surviving objects are copied into a survivor space.
5. Objects that survive repeated collections accumulate age.
6. Objects may eventually be promoted to the Old Generation.

### 3.2 Old Generation

- Holds objects that survive long enough to be promoted.
- Often contains long-lived objects.
- Collection activity is generally less frequent than in the Young Generation in traditional generational collectors.

The promotion age is JVM- and collector-dependent. A threshold of 15 is a commonly cited example, not a fixed Java rule.

## 4. Garbage Collection (GC)

Garbage Collection automatically reclaims heap memory occupied by objects that are no longer reachable.

An object is eligible for GC when it is no longer reachable through any live reference path from a GC Root.

### 4.1 GC Roots

GC Roots are starting points used by the collector to determine object reachability.

Common examples include:

- References in active thread stacks
- Static references
- References from JNI handles
- JVM internal references

If an object is reachable from a GC Root, it is considered live.

```java
Employee employee = new Employee();

employee = null;
```

If no other live reference points to the object, it becomes eligible for garbage collection.

**Eligible does not mean immediately collected.** The JVM decides when collection occurs.

### 4.2 Types of GC Events

In traditional generational GC terminology:

| Type | Description |
|---|---|
| Minor GC | Collects the Young Generation |
| Major GC | Commonly refers to collection of the Old Generation |
| Full GC | Usually involves a broader collection of heap and may include other memory management work |

Terminology varies between JVM implementations and collectors. A Major GC is not universally synonymous with a Full GC.

### 4.3 Garbage Collection Algorithms

#### Mark and Sweep

1. Mark all reachable objects.
2. Identify unreachable objects.
3. Reclaim memory occupied by unreachable objects.

**Limitation:** Can leave fragmented free memory.

#### Mark and Compact

1. Mark reachable objects.
2. Identify unreachable objects.
3. Reclaim their memory.
4. Move surviving objects together to compact the available space.

**Advantage:** Reduces fragmentation.

#### Copying Algorithm

1. Divide memory into regions or spaces.
2. Copy live objects from one space to another.
3. Reclaim the original space.

Commonly used in young-generation collection designs because many newly created objects become unreachable quickly.

## 5. Object References

Java provides different reference strengths through classes in `java.lang.ref`.

| Reference Type | GC Behaviour | Typical Use |
|---|---|---|
| Strong | Prevents collection while strongly reachable | Normal object references |
| Soft | May be cleared when memory is low | Memory-sensitive caches |
| Weak | Does not prevent collection; may be cleared during GC | Weak-key maps, canonicalizing structures |
| Phantom | Object is already phantom-reachable; used to track reclamation | Advanced resource cleanup tracking |

### 5.1 Strong Reference

The normal reference type used in Java.

```java
Employee employee = new Employee();
```

As long as the object remains strongly reachable, GC cannot reclaim it.

### 5.2 Soft Reference

A soft reference does not keep an object strongly reachable. The JVM may clear soft references when it determines that memory is insufficient.

```java
SoftReference<Employee> reference =
    new SoftReference<>(new Employee());

Employee employee = reference.get();
```

The returned value can be `null` if the reference has been cleared.

**Note:** Soft references are not a guarantee that an object will remain cached until memory pressure occurs. Explicit cache eviction policies are generally more predictable.

### 5.3 Weak Reference

A weak reference does not prevent its referent from being collected.

```java
WeakReference<Employee> reference =
    new WeakReference<>(new Employee());

Employee employee = reference.get();
```

If the object has no strong or soft reachability, it may be collected during a subsequent GC cycle.

A common application is `WeakHashMap`, where keys are weakly referenced.

### 5.4 Phantom Reference

- A phantom reference's `get()` method always returns `null`.
- It is used with a `ReferenceQueue`.
- It allows tracking of an object's transition through reclamation.
- It is useful for advanced cleanup coordination, not ordinary object access.

Modern Java code should generally prefer `Cleaner` or structured resource management for resource cleanup rather than relying on finalization.

## 6. Stop-The-World (STW)

Stop-The-World is a pause during which application threads are stopped so the JVM can perform certain GC operations safely.

Important points:

- STW pauses can occur during garbage collection.
- Their duration depends on the collector, heap size, workload and configuration.
- Some collectors perform substantial work concurrently with application threads.
- Concurrent collectors can still require short STW pauses.

### Parallel GC

- Uses multiple threads for garbage collection.
- Can improve collection throughput by using multiple CPU cores.
- Its collection pauses are still STW pauses.

**Interview distinction:**

- Parallel GC: Uses multiple GC threads.
- Concurrent GC: Performs some GC work while application threads continue running.
- Parallel and concurrent describe different aspects of collector behaviour.

## 7. Common Memory Errors

| Error | Meaning | Common Cause |
|---|---|---|
| `StackOverflowError` | Thread stack exhausted | Deep or infinite recursion |
| `OutOfMemoryError: Java heap space` | Heap allocation failed | Too many live objects or insufficient heap |
| `OutOfMemoryError: Metaspace` | Metaspace exhausted | Excessive class metadata or class-loader leaks |
| `OutOfMemoryError: unable to create native thread` | Native thread creation failed | Too many threads or OS resource limits |

### Memory Leak in Java

A memory leak occurs when objects are no longer needed by the application but remain reachable, preventing GC from reclaiming them.

Common causes:
- Static collections retaining objects indefinitely
- Unbounded caches
- Listeners or callbacks that are never deregistered
- Incorrect `ThreadLocal` usage
- Long-lived references to large object graphs

**Important:** Java has automatic GC, but developers are still responsible for managing object reachability.

## 8. Important Interview Questions

**Q1. What is the difference between Stack and Heap?**

- Stack is thread-specific and stores method frames and local variables.
- Heap is shared across threads and stores objects and arrays.
- Stack frames are removed as method calls complete.
- Heap memory is reclaimed by GC.

**Q2. Where are objects and references stored?**

Objects are generally allocated on the heap. Local reference variables are stored in the method's stack frame. A reference can also be stored in an object's field or a static field.

**Q3. What makes an object eligible for GC?**

When it is no longer reachable through any live reference path from GC Roots.

**Q4. Can we force Garbage Collection?**

No. `System.gc()` and `Runtime.getRuntime().gc()` only request or suggest GC. The JVM is not required to perform it immediately.

**Q5. What is the difference between StackOverflowError and OutOfMemoryError?**

- `StackOverflowError`: A thread's stack has exceeded its limit.
- `OutOfMemoryError`: The JVM cannot satisfy a memory allocation request. It can affect heap, Metaspace or native memory.

**Q6. What is the difference between Minor GC and Major GC?**

In traditional generational terminology, Minor GC collects the Young Generation, while Major GC commonly refers to Old Generation collection. Exact terminology and behaviour depend on the collector.

**Q7. What is object promotion?**

When an object survives enough young-generation collections, it may be moved to the Old Generation.

**Q8. What are GC Roots?**

References from JVM-defined starting points, such as active thread stacks and static references, used to determine object reachability.

**Q9. Does setting a reference to null guarantee GC?**

No. It only removes that particular reference. The object is eligible for GC only if no other live reference path reaches it.

**Q10. What is Stop-The-World?**

A pause during which application threads are stopped while the JVM performs certain operations, including parts of garbage collection.

**Q11. Difference between `final`, `finally`, and `finalize()`?**

- `final`: Keyword used for constants, non-overridable methods and non-inheritable classes.
- `finally`: Exception-handling block used for cleanup.
- `finalize()`: Legacy GC-related method, deprecated for removal and not reliable for resource cleanup.

## 9. Quick Revision

- **Stack:** Per-thread; method frames and local variables.
- **Heap:** Shared; objects and arrays.
- **Method Area:** Shared logical area for class metadata.
- **Metaspace:** HotSpot's implementation of the Method Area.
- **PC Register:** Per-thread instruction tracking.
- **GC Roots:** Starting points for reachability analysis.
- **Minor GC:** Young Generation collection in traditional terminology.
- **Old Generation:** Common destination for long-lived objects.
- **Mark & Sweep:** Reclaims unreachable objects; may fragment memory.
- **Mark & Compact:** Reclaims and compacts memory.
- **Copying:** Moves surviving objects to another space.
- **Strong Reference:** Keeps an object strongly reachable.
- **Soft Reference:** May be cleared under memory pressure.
- **Weak Reference:** Does not prevent collection.
- **Phantom Reference:** Supports post-reachability reclamation tracking.
- **STW:** Application threads pause during certain JVM operations.
- **`System.gc()`:** Request, not a guarantee.
- **Memory leak:** Unneeded objects remain reachable.
