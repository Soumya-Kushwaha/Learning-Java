# Generics Wildcards & Type Erasure

## 1. Invariance of Generics

In Java, generic types are **invariant**. Even when one type is a subtype of another, the corresponding parameterized types are not automatically related by the same subtype relationship.

For example, `Integer` extends `Number`, but `List<Integer>` is **not** a subtype of `List<Number>`.

```java
List<Integer> integers = new ArrayList<>();

// Invalid:
List<Number> numbers = integers;
```

Why is this prohibited?

If the assignment were allowed, the following would be possible:

```java
List<Integer> integers = new ArrayList<>();
List<Number> numbers = integers; // Hypothetically allowed

numbers.add(3.14); // A Double enters the list
Integer value = integers.get(0); // Type safety violation
```

A `List<Integer>` must not accept a `Double`. Invariance prevents this kind of type-safety problem.

**Key distinction:** Inheritance between the type arguments does not automatically imply inheritance between their generic containers.

## 2. What Are Wildcards?

The wildcard `?` represents an unknown type argument.

Wildcards allow methods to work with parameterized types whose exact type argument is not known in advance.

```java
List<?> values;
```

This means `values` is a list of some specific but unknown reference type.

It could refer to a `List<String>`, `List<Integer>`, or another parameterized list.

### Unbounded Wildcard: `?`

```java
public static void printAll(List<?> values) {
    for (Object value : values) {
        System.out.println(value);
    }
}
```

Usage:

```java
printAll(List.of("Java", "Python"));
printAll(List.of(10, 20, 30));
```

The method can accept lists with different element types.

**What can you do with `List<?>`?**

- Read elements as `Object`.
- Iterate over the elements.
- Check the size or whether the list is empty.
- Add `null`, because `null` is compatible with every reference type.

**What can you not do?**

```java
List<?> values = new ArrayList<String>();

// values.add("Java"); // Compile-time error
// values.add(10);     // Compile-time error
```

The actual element type is unknown, so the compiler cannot safely allow a non-null value to be added.

## 3. Upper-Bounded Wildcards: `? extends T`

An upper-bounded wildcard represents a type that is `T` or a subtype of `T`.

### Syntax

```java
List<? extends Number> numbers;
```

This can refer to:

- `List<Integer>`
- `List<Double>`
- `List<Float>`
- `List<Number>`

It cannot refer to `List<String>`.

### Reading Values

```java
public static double sum(List<? extends Number> numbers) {
    double total = 0;

    for (Number number : numbers) {
        total += number.doubleValue();
    }

    return total;
}
```

Usage:

```java
System.out.println(sum(List.of(1, 2, 3)));       // 6.0
System.out.println(sum(List.of(1.5, 2.5)));     // 4.0
```

The elements can safely be read as `Number`, because the actual element type must be `Number` or a subtype.

### Why Can't You Add Values?

```java
List<? extends Number> numbers = new ArrayList<Integer>();

// numbers.add(10);   // Compile-time error
// numbers.add(3.14); // Compile-time error
```

The compiler does not know whether the list is a `List<Integer>`, `List<Double>`, or `List<Number>`. Adding a value could violate the actual list's type.

Reading is safe, but adding non-null values is not.

### When to Use `? extends T`

Use an upper-bounded wildcard when a method primarily **consumes values from a source**.

Examples:

- Summing a list of numbers.
- Reading values from a collection.
- Processing objects that share a common parent type.

## 4. Lower-Bounded Wildcards: `? super T`

A lower-bounded wildcard represents a type that is `T` or a supertype of `T`.

### Syntax

```java
List<? super Integer> values;
```

This can refer to:

- `List<Integer>`
- `List<Number>`
- `List<Object>`

It cannot refer to `List<Double>`.

### Adding Values

```java
public static void addIntegers(List<? super Integer> values) {
    values.add(10);
    values.add(20);
    values.add(30);
}
```

Usage:

```java
List<Integer> integers = new ArrayList<>();
List<Number> numbers = new ArrayList<>();
List<Object> objects = new ArrayList<>();

addIntegers(integers);
addIntegers(numbers);
addIntegers(objects);
```

Adding an `Integer` is safe because every permitted list type can store an `Integer`.

### Reading Values

```java
List<? super Integer> values = new ArrayList<Number>();
values.add(10);

Object value = values.get(0); // Valid
```

Elements can only be read safely as `Object` without additional type information, because the actual list might be a `List<Integer>`, `List<Number>`, or `List<Object>`.

### When to Use `? super T`

Use a lower-bounded wildcard when a method primarily **accepts or inserts values of type `T`**.

Examples:

- Adding values to a destination collection.
- Copying values into a destination.
- Passing a consumer that accepts `T` or a supertype.

## 5. PECS Rule

**PECS = Producer Extends, Consumer Super.**

This rule helps decide which wildcard bound to use.

| Purpose | Wildcard | Explanation |
|---|---|---|
| Produce values for your code to read | `? extends T` | Values can be read safely as `T`. |
| Consume values supplied by your code | `? super T` | Values of type `T` can be added safely. |
| Exact type is not important | `?` | The type argument is unknown. |

### Example: Copying Between Collections

```java
public static <T> void copy(
        List<? extends T> source,
        List<? super T> destination) {

    for (T item : source) {
        destination.add(item);
    }
}
```

Usage:

```java
List<Integer> source = List.of(1, 2, 3);
List<Number> destination = new ArrayList<>();

copy(source, destination);

System.out.println(destination); // [1, 2, 3]
```

Why does this work?

- `source` produces values. Its type is `? extends T`.
- `destination` consumes values. Its type is `? super T`.

This is a common practical application of PECS.

## 6. Wildcards vs Type Parameters

Wildcards and named type parameters are related but serve different purposes.

| Feature | Type parameter, such as `<T>` | Wildcard, such as `?` |
|---|---|---|
| Purpose | Names a type that can be referenced elsewhere in the declaration | Represents an unknown type |
| Can connect multiple types | Yes | Not by itself |
| Example | `<T> T identity(T value)` | `void print(List<?> values)` |
| Typical use | Relating input and output types | Accepting a range of compatible parameterized types |

Example using a type parameter:

```java
public static <T> T identity(T value) {
    return value;
}
```

The return type is related to the argument type: passing a `String` returns a `String`.

Example using a wildcard:

```java
public static void print(List<?> values) {
    for (Object value : values) {
        System.out.println(value);
    }
}
```

The method can accept lists of different types but does not need to name the element type.

## 7. Type Erasure

Java implements generics primarily through **type erasure** to maintain compatibility with pre-generics Java bytecode and APIs.

During compilation, generic type information is erased from most runtime type representations.

- An unbounded type parameter generally erases to `Object`.
- A bounded type parameter erases to its leftmost bound.
- The compiler inserts necessary casts where values are retrieved.
- The compiler may generate bridge methods to preserve polymorphism after erasure.

### Example

```java
class Box<T> {
    private T value;

    public void set(T value) {
        this.value = value;
    }

    public T get() {
        return value;
    }
}
```

Conceptually, after erasure, the class behaves approximately like this:

```java
class Box {
    private Object value;

    public void set(Object value) {
        this.value = value;
    }

    public Object get() {
        return value;
    }
}
```

This is a conceptual illustration of erasure, not the exact source code the compiler generates in every detail.

When using `Box<String>`, the compiler knows the declared type and checks assignments at compile time. It inserts appropriate casts when needed.

### Erasure with a Bound

```java
class Calculator<T extends Number> {
    public double convert(T value) {
        return value.doubleValue();
    }
}
```

The type parameter `T` erases to `Number`, its leftmost bound, rather than `Object`.

### Why Type Erasure Exists

- Maintains compatibility with older Java APIs and bytecode.
- Allows generic source code to use the established JVM type system.
- Keeps most generic type arguments out of ordinary runtime type checks.

## 8. Limitations Caused by Type Erasure

### Cannot Use `instanceof` with Most Concrete Parameterized Types

```java
Object value = List.of("Java");

// Invalid:
 // if (value instanceof List<String>) { }
```

At runtime, the JVM cannot generally distinguish `List<String>` from `List<Integer>` through an ordinary `instanceof` check.

However, this is valid:

```java
if (value instanceof List<?>) {
    System.out.println("It's a list");
}
```

`List<?>` is reifiable: the runtime check only needs to determine whether the object is a `List`, without checking its element type.

### Cannot Create Generic Arrays Directly

```java
// T[] values = new T[10]; // Invalid
// List<String>[] lists = new List<String>[10]; // Invalid
```

Generic array creation is restricted because arrays enforce runtime component-type checks, while most generic type arguments are erased.

### Cannot Instantiate a Type Parameter

```java
class Factory<T> {
    // T value = new T(); // Invalid
}
```

The JVM does not know the concrete type represented by `T` in the required form to create an instance this way.

### Cannot Overload by Types That Erase to the Same Signature

```java
// void process(List<String> values) {}
// void process(List<Integer> values) {} // Compile-time error
```

Both methods erase to `process(List)`, so their signatures conflict.

### Generic Type Arguments Are Not Preserved in Ordinary Runtime Checks

```java
List<String> strings = new ArrayList<>();
List<Integer> integers = new ArrayList<>();

System.out.println(strings.getClass() == integers.getClass()); // true
```

Both objects have the same runtime class, `ArrayList`. Their generic arguments do not give them different runtime classes.

## 9. Raw Types

A **raw type** uses a generic class or interface without specifying its type argument.

```java
List values = new ArrayList(); // Raw type
values.add("Java");
values.add(100);
```

Raw types are permitted for legacy compatibility but bypass many generic compile-time checks.

```java
List<String> strings = new ArrayList<>();
List raw = strings;

raw.add(100); // May compile with an unchecked warning

String value = strings.get(0); // ClassCastException at runtime
```

**Best practice:** Prefer parameterized types, such as `List<String>`, rather than raw types, such as `List`.

## 10. Important Gotchas

- **Generic invariance:** `List<Integer>` is not a subtype of `List<Number>`.
- **`? extends T`:** Read values as `T`, but do not add non-null values because the exact subtype is unknown.
- **`? super T`:** Add values of type `T` safely; values are generally read as `Object`.
- **PECS:** Producer uses `extends`; consumer uses `super`.
- **Unbounded wildcard:** `List<?>` can refer to lists of different element types, but arbitrary non-null values cannot be added.
- **Type erasure:** Generic type arguments are not generally available for runtime checks.
- **`instanceof`:** `instanceof List<?>` is valid; `instanceof List<String>` is not generally allowed.
- **Raw types:** They bypass type checks and can introduce runtime `ClassCastException`s.
- **Primitive types:** Generic arguments must be reference types, such as `Integer`, rather than `int`.

## 11. Interview Quick Revision

- **What is invariance?** A subtype relationship between two type arguments does not automatically extend to their generic containers.
- **What is a wildcard?** `?` represents an unknown type argument.
- **What does `? extends Number` mean?** The type argument is `Number` or a subtype of `Number`.
- **What does `? super Integer` mean?** The type argument is `Integer` or a supertype of `Integer`.
- **What is PECS?** Producer Extends, Consumer Super.
- **Why can't you add an `Integer` to `List<? extends Number>`?** The list could actually be a `List<Double>`.
- **Why can you add an `Integer` to `List<? super Integer>`?** Every permitted list type can store an `Integer`.
- **What is type erasure?** The compiler removes most generic type information from runtime representations, replacing type parameters with their bounds or `Object`.
- **Why can't you use `instanceof List<String>`?** Runtime checks generally cannot verify the erased element type.
- **What is a raw type?** A generic type used without specifying its type argument; it weakens compile-time type safety.
- **Why can't `List<String>` be assigned to `List<Object>`?** It would allow non-string objects to be inserted into a list intended to contain strings.
